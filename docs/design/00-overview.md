# 00. 全体の構成

TSX で書いた動画を V8（deno_core）で動かし、AntiWebUI のヘッドレスな文書としてレイアウト・ペイントして、
wgpu で描く。

## スレッド

```
UI スレッド（AntiWebUI App）
  タイムライン・トランスポート（Rust）
  プレビュー = gpu_canvas<Preview>: 届いた Scene を専用の Renderer で描き、箱の中央に置く
        ▲ Arc<Scene>（Send + Sync）          │ seek(frame) / fit(w, h)（最新の希望だけが残る）
プレビューのスレッド（framescript-engine::worker）
  Composition = deno_core の JsRuntime（V8）+ 窓のない AntiWebUI の Ui
  frame → JS の effect → コマンドバッファ → op_fs_commit → update → paint → Scene
```

- UI スレッドはプロジェクトのスクリプトを一切動かさない。重いフレームや V8 の GC でもスクラブは止まらない。
- ワーカーは「描いてほしいフレームと大きさ」を 1 つだけ持つ。描いている間に来た希望は上書きされ、見られない
  フレームは描かない。
- 何もしていない間はプロジェクトとライブラリのファイルを 400 ms ごとに見て、変わったら読み込み直す。読み直した後は
  同じフレームを描き直す。
- コマンドラインの `render` は同じ Composition を、`Gpu::headless()` の Renderer で PNG にする。
  `export`（とスタジオの書き出し）は、それをワーカーの数だけ並べる（「書き出し」）。

## TS → Rust（JSON を使わない）

| op | 種類 | 用途 |
|---|---|---|
| `op_fs_create(kind) -> u32` | fast | ノードを作り、ハンドルを返す |
| `op_fs_commit(Uint32Array)` | fast（`#[buffer] &[u32]` の借用） | 1 フレーム分の変更をまとめて渡す |
| `op_fs_props()` | serde（起動時に 1 回） | プロパティの表（名前・種類・選択肢） |

- コマンドバッファの形式は `crates/framescript-engine/src/commands.rs` の先頭にある。数値は同じメモリに重ねた
  `Float32Array` で書き、Rust は `f32::from_bits` で読む。
- 文字列（テキストと `fontFamily`）も UTF-16 のままバッファに入れる。別の op にすると、バッファの中の
  `UNSET` などと順序が入れ替わるため。
- プロパティの番号は Rust の `props.rs` の表だけが決める。TS は起動時に表を受け取り、名前から番号を引く。
  コード生成は無い。
- シークは `__fs_seek` の `v8::Global<v8::Function>` を持っておき、整数を 1 つ渡して直接呼ぶ。スクリプトの実行や
  serde は通らない。

## TSX

- JSX は classic 変換（`React.createElement`）のまま。ライブラリが `React` をグローバルに定義する。
  pragma も二重のトランスパイルも要らず、ソースマップもそのまま合う。
- モジュールの読み込みは自前の `ModuleLoader`（`loader.rs`）。`"framescript"` と `"framescript/…"` をライブラリの
  ファイルに解決し、TS / TSX は deno_ast で型を取り除いて JSX を変換する（ソースマップは inline で、deno_core が
  スタックトレースに使う）。
- V8 の組み込みの `console` はインスペクタにしか出さないので、ライブラリが `Deno.core.print` で出すものに置き換える
  （`internal/console.ts`）。
- `createElement` は記述を作るだけ。上から順に実体化するので、コンポーネントは親が用意したもの（クリップの
  フレームなど）の中で 1 回だけ動く。コンテキストを渡すコンポーネントは `provide()` を返す（本体で
  `withContext` しても、子の実体化は本体が返った後なので届かない）。
- リアクティブは Solid と同じ考え方で、Clean / Check / Dirty の 3 色（AntiWebUI と同じ）。memo が等しい値を
  返したら下流は動かない。

## 純粋関数としてのフレーム

- `useAnimation` はセットアップ中に 1 回だけ走る。ハンドルの `then` はスクリプトの時計を進めるだけで、待たない。
  `Deno.core.runMicrotasks()` で await の連鎖をその場で流しきるので、終わった時点で長さが決まり、クリップの長さも
  同期的に決まる。ハンドル以外を await すると、流しきれないのでエラーにする。
- 結果は変数ごとのセグメントの列。値はフレームの純粋関数（二分探索）で、変数は memo なので、動いていない間は何も
  伝わらない。
- クリップの相対フレームは表示されていない間は端で止まるので、見えていないクリップの中身も動かない。
- AntiWebUI の `animated` / `transition` は壁時計で動くので、動画の中では使わない。`paint` に渡す時刻はフレームから
  作る。
- `tests/hello.rs`: 例のプロジェクトを 13 フレームおきに順に描いたものと、新しい Composition で逆順に飛んで描いた
  ものが、画素で一致する（Scene はノードの番号が違うので、画素で比べる）。

## 画像と動画

- 画像は AntiWebUI の `img` をそのまま使う（`<img src>`、`objectFit` など）。デコードは AntiWebUI のワーカーで、
  表示される大きさで行い、文書が持つ。フレームを描くときはデコードを待つ。
- 動画は AntiWebUI のプレーヤー（時計で進む）を使わない。フレームは「どう辿り着いたか」によらず同じ絵でなければ
  ならないので、`anti-webui-video` に足した `VideoReader`（時刻を指定したフレームの読み出し）と `show_frame`
  （`video` 要素にアプリが選んだフレームを出す）で作る。
- `<Video src trimStart trimEnd playbackRate>` はクリップのフレームから時刻（秒）を出す memo を持ち、
  `op::VIDEO_TIME` で送る（f64 を 2 語で）。クリップの長さは動画の長さで決まる（`op_fs_video_info` で開いて
  長さを聞く）。クリップの 1 秒前から先読みを頼む。
- エンジン側（`media.rs`）は動画ごとにデコードのスレッドとフレームのキャッシュを持つ。

```
Composition（プレビューのスレッド）                デコードのスレッド（動画ごと）
  JS: 時刻 → VIDEO_TIME                              望まれた時刻ごとに、その後 0.5 秒で欠けている所を探す
  show_frames: 全部の時刻を頼んでから、              少し先（2 秒以内、またはキーフレームへ移動した目的地まで）なら読み進め、
    まとめて最大 15 ms 待つ                          それ以外はキーフレームへ移動。途中のフレームも全部取っておく
  無ければ一番近いフレームを出し、未完成と返す  ←   欲しかったフレームが来たら知らせる → ワーカーが同じフレームを描き直す
```

- キャッシュはデコードしたフレーム（メモリの YUV）。既定で全体 1 GiB（`FRAMESCRIPT_VIDEO_CACHE_MB`）を動画の数で
  分け、超えたら望まれた時刻から遠い方の端から捨てる。望まれた時刻の前後 0.5 秒は捨てない。
- キャッシュは `Media` が持ち、`Composition` より長生きする。スクリプトを直して読み直しても、ファイルが
  変わらない限りデコード済みのフレームはそのまま使える。
- 同じ動画を同時に複数の場所に出せる（望まれた時刻は要素ごと。レンダラー向けのストリームも要素ごと）。
  望まれた時刻が読み進める距離（2 秒）より離れて何か所かにあると、その数だけ（最大 3 本）デコーダを増やし、
  キャッシュは共有する。1 本だと、たとえば同じ動画の 1 倍速と 2 倍速を途中から出したとき、フレームごとに両方の
  キーフレームへ行き来して、1 フレームに 100 ms かかるまで遅くなっていった。
- 書き出しやテストは `Wait::Exact` で、フレームが揃うまで待つ（`tests/media.rs`: 輝度でフレーム番号を埋めた動画で、
  どの順に描いても各フレームがその番号を出すことを画素で確かめる）。
- `FRAMESCRIPT_HWDEC=/dev/dri/renderD128` で VA-API でデコードする（メモリに転送して使う）。この環境（Radeon
  880M）では 1080p の H.264 で CPU と差が無かったので、既定は CPU。

`examples/media`（1080p60 と 720p30、キーフレームは 2 秒おき）での実測（`cargo run --release -p
framescript-engine --example seek`、プレビューは 1280×720）:

| | |
|---|---|
| 再生 | 60 fps で遅れなし、代わりのフレームも出ない |
| 遠くへのジャンプ（動画 3 本） | 何かが出るまで 15 ms、正しいフレームまで中央値 45〜50 ms、最悪 125 ms 程度 |
| 再生した範囲を戻る | 1 フレーム 1.5〜5 ms。キャッシュから外れた所だけ代わりのフレーム |

## 音声

音はフレームごとにスクリプトを走らせて作らない。読み込みのときに一度だけ、どの音がどこにあるかをスクリプトに聞き
（`__fs_audio`）、それ（`AudioPlan`）から任意の区間を混ぜる。プレビューの再生も、いずれ書き出しも同じ関数を使う。

- `<Audio src trimStart trimEnd playbackRate volume fadeIn fadeOut>` はクリップの先頭から鳴り、クリップの長さを
  音の長さにする（`<Video>` と同じ `placeSpan`）。`<Video>` は音があれば鳴らす（`muted` で消す）。
- `volume` が関数なら、読み込み時にクリップのフレームごとに 1 回ずつ呼んで包絡線（フレームごとの値）にし、
  間は直線で補う。シグナルは読めない（どのフレームの値も、そのフレームまで進めずに決まる必要があるため）。
  フェードはサンプル単位で掛ける。
- 混ぜるのは 48 kHz、2 ch、`f32`。速度を変えた音は線形補間で間を取る（テープのように音程も変わる）。
- ファイルごとにデコードのスレッド（`anti-webui-video` に足した `AudioReader`）と、0.5 秒単位のブロックの
  キャッシュを持つ（`sound.rs`）。望まれたブロックとその後 3 秒を先に作り、2 秒以内の先は読み進め、
  それ以外は 0.1 秒手前へ移動する（移動先が後ろだったらさらに戻る）。1 ファイル 64 MB（約 6 分）を超えたら
  遠い方から捨てる。動画と同じく `Media` が持ち、読み直しても残る。
- 時刻の原点は、映像があれば映像のストリームの開始時刻（`VideoReader` と同じ）。動画の音と絵がずれない。

プレビューの再生（`playback.rs` の `AudioPlayer`）:

- 再生中は音が時計になる。デバイスに書いた量 − `snd_pcm_delay` が「今聞こえている所」で、スタジオはその
  フレームを出す。絵の作りが遅れても音から離れない。音が無い、出力先が無いときは壁時計。
- デバイスの値は段々に動くので、壁時計との差を平滑化して使い、時計は戻らない。経過時間より先には進めない
  （何でもすぐ受け取るデバイスでも狂わない）。
- 10 ms ずつ混ぜて書く。デコードが間に合わない所は無音（再生の最初の 100 ms だけ少し待つ）。
- 止めたら捨てる（`snd_pcm_drop`）。手で動かしたら、そこから 80 ms を端をなめらかにして鳴らす。

この環境（PipeWire、`pipewire-alsa`）では `snd_pcm_delay` が約 280 ms を返す（ALSA のバッファ 100 ms に、
PipeWire 側の分が乗る）。再生を始めてから絵が動き出すまでこれだけかかるが、音と絵は揃っている。

確かめたこと（`tests/sound.rs`、`tests/playback.rs`）: サンプル番号を埋めた音で、切り出し・音量の包絡線・
2 倍速・フェード・動画の音が、混ぜた結果の位置と値で正しいこと。ファイルに書く ALSA のデバイスで、
再生したものが混ぜたものとサンプル単位で一致し、時計が戻らず経過時間を超えないこと。耳では確かめていない
（`examples/media` の counter は毎秒の頭で鳴るので、数字が変わる瞬間と合っていれば揃っている）。

## 書き出し

```
書き出しのスレッド: 1 回読み込んで長さ・大きさ・音の計画を得る → 下を始めて、100 ms ごとに進み具合を伝える
  ワーカー × N（それぞれ Composition + GPU デバイス + ffmpeg）
    自分の区間を前から順に: render(f) → GPU で YUV 4:2:0 → 2 フレームのキュー → ffmpeg の stdin → part-<先頭フレーム>.mp4
    自分の区間が空になったら、残りが一番多いワーカーの後ろ半分をもらう（1 秒分の 2 倍未満なら分けない）
  音のスレッド: AudioPlan::mix を 1 秒ずつ → sound.f32
→ 全部終わったら ffmpeg の concat で部品を並べ、映像はそのまま（-c copy）、音はここでエンコードして入れる
```

- エンコードはシステムの `ffmpeg` コマンドに生のフレームを流す（`FRAMESCRIPT_FFMPEG`）。デコードと違って
  ライブラリを dlopen しないのは、エンコーダの設定（AVCodecContext の多くのフィールド）を手書きの
  オフセットで扱うと、FFmpeg の版ごとに壊れ方が増えるため。コマンドなら H.264 / H.265（x264, x265）、AV1
  （SVT-AV1）、ProRes、VA-API がそのまま使える。使えるものは `ffmpeg -encoders` で調べ、GPU のものは 1 フレーム
  エンコードして確かめる。
- フレームは番号の純粋関数なので、どのワーカーがどの順に描いてもよい。区間を細かく交互に配ると、各ワーカーの
  動画が区間ごとにキーフレームへ戻ってデコードが倍近くになったので、区間は大きく取り、早く終わったものが
  他の残りの後半を取る（work stealing）。部品のファイルは先頭のフレームの番号で名前を付け、名前順に並べる。
- 部品は MP4（ProRes は MOV）で、タイムスケールをフレームレートの倍数にする（60 fps なら 10020、29.97 なら
  30000）。concat で並べても各フレームの時刻がずれない（B フレームありで、150 フレーム・1001 刻みに抜けが
  無いことを確かめた）。
- 色: GPU の計算シェーダで RGBA（ガンマのかかった値のまま）を BT.709・ビデオレンジの YUV 4:2:0 にする（色差は
  2×2 の平均）。読み戻しが 8.3 MB から 3.1 MB になり、ffmpeg の変換（x264 の CPU 時間の約 25%）が無くなる。
  swscale の 4:2:0 と比べて同じ PSNR。ProRes だけは RGBA を渡して ffmpeg が 4:2:2 10 bit にする。
- 大きさは 50〜200%。100% を超えても、レイアウトはプロジェクトの大きさのまま倍率を上げて描くので、文字や図形は
  ぼけない（`Composition::scale_to`）。
- 音は `AudioPlan` を f32 で書き出し、最後に AAC（ProRes では PCM）にする。範囲を指定したら、その範囲だけ。
- 書き出し中のワーカーは動画のキャッシュを 512 MB ずつ持つ。止めるとワーカーは次のフレームで止まり、ffmpeg は
  殺され、部品のディレクトリ（出力の隣の `.<名前>.framescript-<pid>`）は消える。
- スタジオでは、トランスポートの右の映画のボタンで書き出しのウィンドウ（`open_window` の dialog）が開く。
  進み具合はスタジオの窓のチャネルに届くので、書き出しのウィンドウを閉じても続き、トランスポートに % が出る。
  スタジオを閉じたら止める。

この環境（Ryzen AI 9 365、20 スレッド、Radeon 880M、電源プロファイルは balanced）での実測:

| | ワーカー 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| `examples/media`（1080p60、14 s、x264 medium CRF 18） | 5.1 s | 4.4 s | 5.2 s | 7.2 s |
| 1500 個の箱と文字が毎フレーム動く 10 s（レイアウト 45 ms/フレーム） | 58.7 s | 35.8 s | 25.0 s | 25.3 s |

- 描くことが重いときはワーカーで速くなり、x264 が CPU を使い切るところで止まる。軽いプロジェクトでは最初から
  x264 が律速なので、ワーカーを増やすとエンコーダどうしが CPU を取り合って遅くなる。既定はスレッド 5 本に 1 つ
  （ここでは 4）。
- 描くだけなら（エンコーダを捨てる ffmpeg に替えて）`examples/media` は 1 ワーカーで約 330 fps。GPU で描いて
  読み戻すのが 1 フレーム約 1.75 ms で、iGPU が 1 つなのでワーカーを増やしても重ならない。
- VA-API の H.264 は `examples/media` で 4.0 s（エンコードはほぼ只）。どのときも Vulkan のデバイスを作るのに
  約 1 秒かかる（プロセスで 1 回）。

確かめたこと（`tests/export.rs`）: 灰色でフレーム番号を埋めた 120 フレームを、ワーカー 3 つ・ロスレスで
書き出し、全フレームの Y が期待した値と一致する（抜けも重複も順番違いも無い）。ProRes では音が混ぜたものと
サンプル単位で一致する。範囲を指定したら、その最初のフレームから始まり音の長さも合う。止めたら何も残らない。

## WGSL と 3D

```
スクリプト ── op_fs_shader(code, path, stage) ──▶ naga で解析・検証、@group(1) を読む ──▶ ShaderInfo
   │                                                    （誤りはその場で JS の例外。ファイル名:行:列）
   └── コマンド: PARAM / PARAM_TEXT（変わった値だけ）
          ▼
   Drawn（コンポジションのスレッド）: <Shader> の箱、3D の物の木（Spaces）、画像
          │ フレームのコマンドが揃ったら、変わった箱だけスナップショットを作る
          ▼
   portable canvas の props（Arc、Send + Sync）── Scene に載る
          ▼
   Scene を描く renderer が、自分の device で FlatPaint / SpacePaint を作って描く
   （プレビューは UI スレッド、書き出しは各ワーカー）
```

- **なぜ描き手を Scene に載せるか**: AntiWebUI の `gpu_canvas` は描き手が文書のスレッドのスレッドローカルにあり、別スレッドの renderer からは見えない。FrameScript2 はコンポジションのスレッドで塗った `Scene` を別のスレッドで描く。そこで AntiWebUI に「持ち運べる canvas」を足した（AntiWebUI の 41 番）。`Scene` には「何から描くか」だけが載り、描き手は描く側が作る。シークでも並列書き出しでも、フレームは番号の関数のまま。
- **WGSL の組み立て**: コンポジションのコードを先に、FrameScript が足すもの（`fs`、全画面の三角形、3D のライティングなど）を後に置く。WGSL は宣言の順を問わないので、エラーの行番号がそのファイルの行になる。`.wgsl` はローダーが「コードを default export するモジュール」にし、ファイル名を覚えておく。
- **uniform**: naga で `@group(1)` の uniform の構造体を読み、メンバーごとに数がどのオフセットに入るか（vec3 の 16 揃え、行列の列の幅、配列の stride）を求める。スクリプトは名前で値を渡し、Rust が WGSL の配置どおりに詰める。CSS の色は JS 側でリニアに直す。名前の誤りは「did you mean」付きの例外になる。
- **3D の物**: 文書のノードとは別の木（`space::Spaces`）。ハンドルの名前空間は共通で、`CHILDREN` はシーンの箱では 2D の子と 3D の根に分かれる。`<Clip>` はシーンの中では `visible` で出入りするグループになる（`SpaceContext`）。
- **描き方**: 4× MSAA の half float にリニアの光で描き、最後に sRGB にしてプリマルチプライドで箱に書く。不透明な物を先に、透けて見える物を遠い順に後で描く。トーンマッピングは光を受ける面だけ、そのフラグメントシェーダーで行う（three.js と同じ）。背景と `fragment` を書いたマテリアルは、指定した色がそのまま出る。光の強さ 1 は、白い面を正面から照らすと白になる値。
- **マテリアルの WGSL**: `surface(in) -> Surface`（`default_surface(in)` から始める）、`fragment(in) -> vec4f`（光を使わない）、`vertex(v) -> Vertex` のどれでも書ける。書かなかったものは FrameScript の既定が使われる。標準マテリアルは空のコードを同じ方法でコンパイルしたもの。
- **影**: `castShadow` の平行光とスポット（4 つまで）が、2048×2048 のシャドウマップ（深度の配列テクスチャの 1 層ずつ）を描く。平行光の範囲は「影を落とす物」のバウンディングボックスを光の空間に移した XY と、全ての物の奥行きから自動で決める（影は光の向きに落ちるので、XY は影を落とす物の範囲で足りる）。スポットは円錐の角度の透視投影。シャドウマップを描くパスはマテリアルの `vertex` も通すので、動かした頂点の影になる。自己影はテクセル 1.5 個分の法線方向のずらしと slope の深度バイアスで避け、比較サンプラーの 3×3 で縁をぼかす。メッシュは既定で影を落とし受ける。点光源の影（キューブマップ）はまだ。
- **glTF（`<Model>`）**: gltf クレートで一度だけ読み（`Drawn` がファイルごとに持つ）、時刻から姿勢を作る純粋関数にする。アニメーション（linear、step、cubic spline の平行移動・回転・拡大）をその時刻で取り出し、ノードの変換を根から計算し、スキンは CPU で曲げて形をその都度作る（形の id が毎回変わるので、描く側は前のバッファを捨てて作り直す）。GPU でのスキニングより遅いが、狐（約 1700 頂点）なら気にならず、形がシーンのスナップショットに入るので影も同じ形になる。マテリアルはベースカラー（値と画像）、metallic / roughness の値、emissive（と強さの拡張）、両面、`BLEND` を読む。`modelInfo` で名前と長さを返し、名前の誤りは持っている名前を添えて例外にする。
- **動画のテクスチャ**: `{ video: … }` は文書の木に入らない動画ノードを作る。`<Video>` と同じ `videoClock`（クリップの中の時刻、先読み、音）で時刻が決まり、`MediaNodes` が他の動画と同じくデコードとフレームの待ち合わせをする。同期でそのノードの今のフレーム（`Arc<VideoFrame>`）をスナップショットに入れ、フレームの id が変わったときだけシーンを渡し直す。描く側は、フレーム 1 枚だけの AntiWebUI の Scene を AntiWebUI の Renderer でテクスチャに描く。YUV の形式、色の行列、回転、dmabuf は窓に描くときと同じものが使われる。
- **`<Panel>`**: 中身は `<Scene3D>` の箱の 2D の子として普通にレイアウトされるが、AntiWebUI の「画面の外」の印（`Document::set_offscreen`）が付いていて、文書の絵には出ず、周りのクリップも受けない。同期で `paint::paint_node` によりその部分木だけを Scene に塗り、前と同じなら前の `Arc` を使い回す（描く側はポインタが変わったときだけテクスチャを描き直す）。テクスチャは原点をずらした Layer で描く。AntiWebUI の出力はプリマルチプライドなので、マテリアルの印で戻してから使う（sRGB のままプリマルチプライドされた値を光に直すので、べき 2.2 で近似して割る）。既定は光を受けず、色がそのまま出る。同期はこのため、レイアウトの後・ペイントの前に移した。
- **エフェクト**: シーンを描いた後の半精度のテクスチャに、順に掛ける。WGSL のエフェクトは 2 枚のテクスチャを交互に読み書きする。ブルームは半分の大きさから最大 6 段の縮小（13 点）と拡大（9 点のテント、足し合わせ）で、最後にシーンに足す。トーンマッピングはマテリアルの中で済んでいるので、閾値は「1 が白」の値で決める。
- **形**: 箱、球、板、円柱（円錐）、トーラスは three.js と同じパラメータで CPU で作り、パラメータごとに共有する。`Mesh` は頂点を直接渡す。

確かめていること（`tests/gpu.rs`）:

- uniform の色がそのままの色で出る。`fs.frame` がクリップのフレームになる。関数の uniform が追従する。
- WGSL の誤りは `bad.wgsl:2:` の形で、uniform の名前違いは「did you mean color?」で読み込みが失敗する。
- 正射影のカメラで、物が置いた画素に描かれ、手前の物が奥の物を隠す。シーンの中の `<Clip>` が時刻で出入りする。
- 画像が `textures` と `map` で渡る。シーンの外に 3D の物を置くと例外になる。
- テストの中で書いた glTF（データ URI のバッファ）で、ノードのアニメーションとスキンのアニメーションが、半秒の時点で半分だけ動いている。無いアニメーションの名前はエラーになる。
- 1 秒ごとに赤と青が替わる動画が、`<Shader>` とクリップの中の板のテクスチャで、それぞれの時刻の色で出る（巻き戻しても）。
- `<Panel>` の中身が、ピクセル数と `pixelsPerUnit` どおりの大きさで物の位置に出て、文書の絵には出ず、中身の変化に追従する。
- 色を反転するエフェクトと関数の uniform、白い円の周りがブルームでだけ明るくなること。空のシーンが背景色になること。
- 斜めの平行光で、箱の影が床の片側にだけ落ちる。`castShadow` の無い光、`receiveShadow={false}` の床では落ちない。
- `examples/3d` のフレームは、前にどのフレームを描いたかによらず同じ。

`examples/3d` を 1920×1080 で 3 ワーカーで書き出すと 780 フレームを 5.0 秒で描いた。

## 依存関係の事情

- JS のランタイムは rustyscript ではなく deno_core（0.413、V8 150）を直接使う。rustyscript は最新の master でも
  deno_core 0.380（V8 142）で、V8 142 の Temporal（temporal_rs 0.1.2）は ICU 2.1 向け、AntiWebUI の parley 0.12 は
  ICU 2.3 以降を求める。ICU のクレートは全体で同じマイナー版でなければならないので、パッチなしでは両立しない。
  V8 149 以降は temporal_rs 0.2（ICU 2.2 以降）になっていて、この問題が無い。crates.io の rustyscript 0.12.3 は
  さらに、deno_ast 0.49 の swc が serde の内部 API（1.0.220 で改名）を使っていて新しい serde と両立しない。
- rustyscript から使っていたのはモジュールの読み込み（TS の変換）、イベントループの駆動、`console` だけだった。
  それぞれ `loader.rs`、`Composition::load` の current-thread の tokio、`internal/console.ts` で置き換えた。
- deno_core 0.413 は `JsRuntime` を tokio のランタイムの中で作ることを求める（V8 が後で走らせるタスクを投げるため）。
  `Composition` がランタイムを持ち、その中で作る。
- AntiWebUI の wgpu のフォークは、依存するワークスペースごとに `[patch.crates-io]` を繰り返す必要がある。
  WGSL の解析に使う naga も同じパッチでフォークのものになり、wgpu が内部で使うものと一致する。
- 3D の行列は glam、`textures` と `map` の画像のデコードは image（AntiWebUI と同じ 0.25）を使う。

## まだのもの

- 音声: タイムラインに波形を出すこと、クリップの境目のプチノイズを消す短いフェード、音程を変えない速度変更、
  書き出し時のラウドネスの正規化。
- プレビュー用に縮小したフレームのキャッシュ（今は元の解像度で持つので、4K だとすぐ予算に達する）。
- 画像は描くときにデコードを待つので、大きな写真が初めて出るフレームは遅い。先読みしたい。
- アニメーション GIF などは AntiWebUI が時計で進めるので、フレームの関数になっていない。
- 書き出し: 透明（アルファ付きの ProRes 4444 など）、連番画像、ファイルを選ぶダイアログ（今は道を書く）、
  GPU の読み戻しを待たずに次のフレームを描くこと。
- 描いたフレームのキャッシュ（RAM プレビュー）、先読み、スクラブ中の低解像度。
- 3D: 点光源の影、glTF のモーフターゲット・metallic-roughness / 法線 / オクルージョンの画像・`MASK` の切り抜き・
  ファイル内のカメラとライト、GPU でのスキニング、HDR の環境マップ、テクスチャのミップマップ、`<Panel>` を
  高い解像度で塗ること、2D 要素に掛ける WGSL の `filter`（AntiWebUI の改修が要る）。2D 要素の CSS 3D 変形は当面やらない。
- `waitUntilClip` は先に作られたクリップしか探せない（後ろのクリップを指すには、長さが決まるまで繰り返す必要がある）。
